Event-Driven: Module kommunizieren über Events, nicht direkte Aufrufe
Single Responsibility: Jeder Service hat genau eine Verantwortung
DRY: Shared Code in /src/shared/ — aber KEINE vorzeitige Abstraktion
KISS: Einfachste Lösung die funktioniert > Overengineering
Resilience: Jeder externe Call hat Timeout, Retry und Fallback
Observability: Logging, Metrics, Tracing für jeden kritischen Pfad
ENTSCHEIDUNGS-FRAMEWORK:
Wenn du eine Architektur-Entscheidung triffst, dokumentiere sie als ADR:

markdown# ADR-[NNN]: [Titel]
**Status:** Proposed | Accepted | Deprecated | Superseded
**Context:** Warum brauchen wir diese Entscheidung?
**Decision:** Was haben wir entschieden?
**Consequences:** Was bedeutet das?
**Alternatives Considered:** Was haben wir verworfen und warum?
```

DATEN-FLUSS FÜR CONTENT GENERATION:
```
User Request (UI)
    ↓
API Gateway (Cloud Run)
    ↓
Campaign Service → Erstellt Task
    ↓
Pub/Sub Event: "task.created"
    ↓
Agent Runtime Service
    ├─ Context Assembly (Firestore + Knowledge Base)
    ├─ Agent Selection (SP-01 für Strategie, CC-06 für Content)
    ├─ Vertex AI API Call (Gemini 2.0 Pro)
    ├─ Output Parsing & Validation
    └─ Pub/Sub Event: "content.generated"
    ↓
Senate Service → Compliance Check
    ├─ Policy Evaluation
    ├─ Risk Scoring
    └─ Pub/Sub Event: "content.reviewed"
    ↓
Content Service → Speichern in Firestore
    ↓
Pub/Sub Event: "content.stored"
    ↓
Notification Service → User benachrichtigen
    ↓
Analytics Service → Metriken aktualisieren
```
INTER-MODUL KOMMUNIKATION (Frontend):
Module kommunizieren über:
1. Zustand Stores (für Shared State)
2. URL Parameters (für Deep Linking)
3. Custom Events (für lose Kopplung)
4. React Query Cache (für Server State Sharing)
NIEMALS:
- Direkte Imports zwischen Modulen (außer shared/)
- Zirkuläre Abhängigkeiten
- Globale Variablen (window.*)
- localStorage für kritischen State
```
