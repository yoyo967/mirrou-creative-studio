## TEIL 2: KERNFLÜSSE (End-to-End Pipelines)
### FLOW 1: Content-Generierungs-Pipeline
```
1. USER → Genius Console: "Schreib einen Blog über KI im Marketing"
2. Genius Console → Agent Router: Task erstellen (type: 'blog')
3. Agent Router → SP-01 (Strategy): Outline + Keywords generieren
4. SP-01 → Knowledge Base: Relevante Quellen suchen (RAG)
5. SP-01 → Brand Voice: Tone/Style laden
6. SP-01 Output → CC-06 (Content): Volltext schreiben
7. CC-06 → Vertex AI (Gemini 2.0 Pro): Generierung
8. CC-06 Output → VS-02 (Visual): Featured Image generieren
9. VS-02 → Vertex AI (Imagen 3): Bildgenerierung
10. CC-06 + VS-02 Output → Security Senate: Compliance-Check
11. RA-01 → Policy Engine: Regeln prüfen
12. Senate Decision → Content Service: Status auf 'approved'
13. Content Service → Blog Engine: Artikel verfügbar
14. Content Service → Asset Vault: Bild gespeichert
15. Content Service → Project Memory: In History gespeichert
16. Notification → User: "Blog-Artikel fertig zur Überprüfung"
17. USER → Blog Engine: Überprüfen, editieren, veröffentlichen
18. Blog Engine → Distribution Engine: Auf Website publizieren
19. Blog Engine → Content Calendar: Im Kalender markieren
20. Distribution → Social Media: Teaser-Posts generieren und posten
21. Analytics → Performance: Engagement tracken
22. Analytics → Billing: Token-Kosten berechnen
23. Audit Log: Jeder Schritt dokumentiert
```
### FLOW 2: Kampagnen-Lifecycle
```
1. USER → Campaign Hub: Neue Kampagne erstellen
2. Campaign Hub → Campaign Service: Kampagne in Firestore speichern
3. Event: campaign.created
4. USER → Campaign Hub: "Execute Campaign" klicken
5. Campaign Service → Workflow Engine: Standard-Workflow starten
6. Workflow Engine → SP-01: Strategie entwickeln
7. SP-01 → Columna Radar: Wettbewerber-Daten laden
8. SP-01 → Knowledge Base: Markt-Insights laden
9. SP-01 Output → CC-06: Content für alle Kanäle generieren
10. CC-06 → Blog, Social, Email, Ad Content (parallel via Task Groups)
11. Alle Outputs → Senate: Batch-Review
12. Approved Content → Distribution Engine: Publishing-Queue
13. Distribution Engine → Content Calendar: Zeitplan erstellen
14. Distribution Engine → Kanäle: Veröffentlichen
15. Performance Analytics → DA-03: Ergebnisse analysieren
16. DA-03 → Campaign Hub: KPIs aktualisieren
17. DA-03 → Notification: Weekly Report an User
18. Bei Kampagnen-Ende → Project Memory: Archivieren mit Learnings
19. Audit Log: Kompletter Kampagnen-Trail
```
### FLOW 3: Echtzeit-Monitoring
```
1. Dashboard → Analytics Service: KPIs pollen (30s Intervall)
2. Dashboard → Firestore Listener: Agent-Status live
3. Swarm Analytics → Agent History: Throughput berechnen
4. Synergy Map → Firestore Listener: Datenflüsse live
5. Billing → Token Counter: Kosten live
6. Notification Center → Firestore Listener: Neue Alerts
7. Anomaly Detection: Wenn Error Rate > Threshold → Alert
8. Perfect Twin → Health Check: System-Gesundheit
```

## TEIL 3: VERTIKALE TIEFE — DATENFLUSS PRO MODUL
### Dashboard — Vertikaler Schnitt
```
[User öffnet /os]
    ↓
Dashboard.tsx mounted
    ↓
useQuery('dashboard-kpis') → GET /api/v1/analytics/dashboard
    ↓                              ↓
    ↓                         analyticsService.getDashboardData()
    ↓                              ↓
    ↓                         Firestore: analytics/{today} + agents/* + campaigns/*
    ↓                              ↓
    ↓                         Response: { kpis, throughput[], agentStatus[], recentActivity[] }
    ↓
KPIGrid renders 6 cards    ThroughputChart renders    SwarmTelemetry renders
    ↓                              ↓                        ↓
KPICard: onClick →          Recharts AreaChart         AgentStatusCard × 6
navigate to module          with 24h data              Firestore onSnapshot
    ↓                                                  (real-time status LED)
ActivityFeed renders
    ↓
ActivityItem × 10
onClick → navigate to source module
```
### Genius Console — Vertikaler Schnitt
```
[User öffnet /os/genius]
    ↓
GeniusConsole.tsx mounted
    ↓
SessionList loads (Firestore: sessions/* where userId == currentUser)
    ↓
User types message in ChatInput
    ↓
ChatInput.onSubmit:
  1. Store message in Firestore: sessions/{id}/messages
  2. POST /api/v1/agents/execute { type: 'chat', input: { message, sessionId } }
     ↓
  3. Backend: agentRuntime.routeChat(message)
     - Analyze intent → select agent (SP-01 for strategy questions, CC-06 for content, etc.)
     - If "Auto" mode: classify intent via lightweight Gemini call
     ↓
  4. Agent.execute() with full session context
     - assembleContext: load session history + relevant knowledge + brand voice
     - Vertex AI Gemini 2.0 Pro (streaming via SSE)
     ↓
  5. SSE Stream back to frontend
     ↓
ChatMessage renders progressively (token by token)
    ↓
If agent generates artifact (image, code, table):
  ArtifactPreview renders inline
    ↓
TokenCounter updates live
    ↓
Session auto-saved to Firestore
```
### Workflow Execution — Vertikaler Schnitt
```
[User clicks "Run Workflow" on Workflows page]
    ↓
POST /api/v1/workflows/{id}/execute
    ↓
WorkflowExecutionEngine.executeWorkflow(id)
    ↓
1. Load workflow definition (nodes + edges) from Firestore
2. Create WorkflowRun document in Firestore
3. Topological sort of DAG nodes
4. For each node in order:
    ↓
    [TriggerNode] → Check trigger condition → Pass
    ↓
    [AgentNode: SP-01] → AgentRegistry.route('strategy')
        → SP-01.execute({ task }) → Vertex AI → Output
        → Store in nodeResults map
        → Pub/Sub: workflow.node.completed
        → Firestore: Update run.nodeResults
    ↓
    [ConditionNode] → Evaluate condition against previous output
        → Branch: true path or false path
    ↓
    [AgentNode: CC-06] → Content generation
        → Same execution pattern as SP-01
    ↓
    [ActionNode: Senate] → Submit to Senate
        → Create senate case
        → Wait for decision (async callback or polling)
    ↓
    [ActionNode: Store] → Save to Firestore
    ↓
    [ActionNode: Notify] → Create notification
    ↓
    [EndNode] → Mark run as completed
    ↓
5. Pub/Sub: workflow.completed
6. Frontend: Firestore listener updates ExecutionLog in real-time
7. RunDetail shows node-by-node timeline with green/red status
```
